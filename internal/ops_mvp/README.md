# 접수→진단→합의→실행→자료→보고 연결 시험실

목적: PR25에서 준비한 양식을 실제 한 고객 흐름으로 연결해 검증한다. 대상: 디테일랩 운영자·개발/검수 담당. 수정: 2026-10-20. 버전: 0.1. 상태: **합성 전용 개발·검수용, 공개·실고객 운영 미승인**. 코드/시험: ChatGPT, 실제 운영·자료 처리 승인: 디테일랩 운영자. 재검토: 첫 현장 시험·자료 형식·권한/처리 조건 변경 때.

공개 홈페이지·기존 무료 도구·센터 베타에는 연결하지 않는다. 실행마다 발급하는 테스트 키와 고정된 합성 고객만 사용한다. `127.0.0.1` 밖에 노출하거나 터널·역방향 프록시를 붙이지 않는다. 표준 라이브러리 HTTP 서버는 운영용 서버가 아니다.

## 직접 실행하기

저장소 루트에서 Python 3.12와 `openpyxl==3.1.5`를 사용한다. 새 유료 계정이나 외부 API 키는 필요하지 않다.

```sh
python3 -m internal.ops_mvp.server --root /tmp/detail-lab-synthetic-trial --port 8765 --seed-complete-case
```

브라우저에서 `http://127.0.0.1:8765`를 연다. 실행 결과에 나온 `test-credentials.json`에서 SYN-OPERATOR(운영자), SYN-OWNER-A/B(가상 고객)의 이번 실행 키를 각각 사용한다. 다른 브라우저 프로필/시크릿 창에서 역할별로 열면 같은 업무를 양쪽 자리에서 확인할 수 있다. 실제 계정 비밀번호를 입력하지 않는다. 키는 재시작 때 바뀌고 세션은 15분 뒤 만료된다. runtime은 저장소 밖에만 둔다.

`--seed-complete-case`는 접수 기록이 없는 새 시험 폴더에만 완결된 합성 사례를 넣는다. 고객 A와 운영자 목록에 그 사례가 보인다. 새 문의를 실제로 시험하려면 고객 A 창의 ‘업장 상황 이야기하기’에서 입력한다. 고객 B 창에서는 A의 사례를 열 수 없다. 재실행을 위한 무단 초기화/삭제 기능은 없다. 새 임시 경로를 쓰면 이전 시험을 보존할 수 있다.

이 승인은 합성 계정의 동작 시험이다. 실제 대표가 합의하거나 실제 사람이 수치를 검수했다는 증거로 쓰지 않는다. 외부 이메일은 자동/수동 모두 발송하지 않는다. ‘안내한 내용’ 필드는 **발송 기록이 아니라 입력한 안내 메모**다.

## 기존 노션과의 연결

- I01~I09/U01~U13/D01~D10: [접수·인터뷰·진단 v2](https://app.notion.com/p/3fef6ead7401812f9480e6f5549c0316). 화면에는 첫 질문과 대체 질문을 넣고, 전체 심층 질문은행은 기존 문서를 사용한다.
- 목표·실험·주간/월간/연간 출력: [기존 합의·실험·보고 양식](https://app.notion.com/p/3fff6ead74018174923cc832cce3da75).
- 자료 정의/단위/출처/권한: [기존 데이터 기준](https://app.notion.com/p/3fef6ead74018152a04ccaf57cc0a522).
- 문서·실험 DB를 새로 만들지 않는다. 기존 합성 실험 행에 실행 증거를 연결하며, 실제 고객 연락/원본은 Notion 공통 DB와 공개 GitHub에 넣지 않는다.
- 노션과 시험 DB 사이의 실시간 동기화는 없다. 공통 기준·변경 상태만 노션에 수동 검수해 기록한다. 고객의 원문을 자동 복사하는 코드는 없다.

## B와 C 사이에서 실제 재사용하는 것

`workflow.py`는 기존 `internal/data_mvp/pipeline.py`의 `Store.add_metric/ingest/review/report`를 호출한다. 같은 이름의 지표를 임의 합산하지 않는다. 이번 시험은 정의가 고정된 `missed_handover v1 (건)`와 `handling_minutes v1 (분)` 두 **가산 가능한 일별 합계**만 지원한다. 비율/평균/재방문율/매출 인식 등 다른 지표는 등록·분모·집계법 검증을 따로 구현해야 한다.

운영 DB: 고객사→여러 사업장→접수→인터뷰→근거/주장→선택 진단→합의 버전→실험→관측/결정→자료 버전→보고. 연락처 DB는 분리하고 관리자 경로에서만 읽는다. 고객별 자료 DB는 기존 처리기의 분리 구조를 유지한다. 각 조회와 변경의 고객/사업장 범위는 서버가 세션의 Actor로 정한다. 브라우저가 보내는 role/client_id를 권한 근거로 쓰지 않는다.

입력 오류는 코드만 반환한다. 운영자 계정은 승인 전에 검증된 행·단위·출처/버전을 미리 볼 수 있고, 이 열람은 이벤트로 남는다. 현재 화면은100행까지 보여주며 더 큰 자료는 일부만 보고 승인하지 않도록 화면 승인을 막는다. 서버의 운영자 승인 API는 별도 수동 원본 검토도 허용하므로 UI 버튼 차단을 보안 경계로 설명하지 않는다. 자료 파일은 임시 경로에서 처리 후 정리하며 원본 파일명/원문을 로그에 남기지 않는다. 서버 프로세스 오류 로그에는 상태·오류 코드만 기록한다. 성공 응답이 오지 않으면 ‘접수 완료’로 표시하지 않고, 같은 접수 키/자료 코드로 재시도한다. 원본 파서가 먼저 저장하고 연결 단계가 실패한 경우 재시도로 같은 버전을 연결하므로, 장애 응답을 ‘아무것도 저장되지 않았다’고 설명하지 않는다. 분산 작업 큐·보장된 재처리 서비스는 아니다.

보고는 외부 AI 없이 입력값에서 계산한다. 수치마다 source_id/version/row_key/date/value를 보존한다. 관측하지 않은 날은 0으로 채우지 않고, 14일 자료로 연간 추세를 만들지 않는다. 새 자료/판단/작업시간 등 입력이 바뀌면 이전 보고의 fingerprint가 달라져 재검수한다. 진단 근거가 바뀌면 기존 목표 승인으로 실행할 수 없고 새 버전을 합의해야 한다.

## 아직 운영 준비가 아닌 이유

- 고정 합성 고객/지표만 있다. 사용자 가입, MFA, 운영용 인증/권한 회수 관리 화면, SSO, 권한 점검 체계 없음.
- 루프백 HTTP만 사용한다. TLS·운영 서버·비공개 파일 저장·저장 암호화/키 관리·상시 접근 모니터링·자동 백업/삭제 전파·재해 복구 없음. 로컬 파일 분리·chmod·세션 시험은 운영 보안 인증이 아니다.
- 자유 문장의 개인정보를 완벽히 판별하지 못한다. 일부 패턴 차단과 `SYN-` 접두사는 실고객 입력을 안전하게 만드는 장치가 아니다. 실제 자료 사용 금지를 해제하는 옵션은 없다.
- 동시 사용/대량 파일/침투시험·실기기·인앱·스크린리더·운영 장애 대응은 미검증. 다중 DB 저장은 분산 트랜잭션이 아니며 연결 실패는 같은 요청으로 수동 복구하는 시험 수준이다.
- 개인정보 처리 주체·목적/항목·보관기간·삭제/권리행사·위탁/국외 이전·AI 처리·계약의 법적 적합성은 별도 확인·검토가 필요하다. 실고객용 동의/처리방침이 아니다.
- 새 공개 접수·실제 고객 자료 저장·유료 인프라/가격·외부 AI/통계 API·고객 발송은 별도 승인 사항이다. 이번 PR 공개 승인만으로 이 항목을 승인했다고 해석하지 않는다.
